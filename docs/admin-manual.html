01Start here

What the lab is, and what it is not

The lab is a workshop for designing models, not a database. You open it, point it at a copy of some organisation's data, and try out different ways of reading that data — what counts as a relationship, what counts as a fact about one organisation, what gets drawn and what does not. When a way of reading proves itself, that model is what ships to the organisation's own website.

It is not where anybody's real data lives, and it is not a place anyone outside this room should be sent. Three organisations are modelled in it today — the Barlavento community, Quinta Vale da Lama, and CoFundEco — plus a blank example to fork from.

The sentence everything else follows from

A client's map is this app plus a model plus a settings file. The data is not part of the package. Each client site fetches its own data, from its own source, on its own schedule — and it would keep doing so if the lab were deleted tomorrow.

02The one idea

Attributes are not relationships

This is the whole reason the tool exists, and it takes one example to see.

Three organisations are all in Bensafrim. Recorded as relationships, that is a triangle of three lines — and with fourteen organisations it becomes a thicket that looks like a finding when it is really an artefact of how the data was typed in. Being in Bensafrim is a fact about each organisation separately. It belongs on the circle, as a colour, not between circles as a line.

Barlavento has 23 recorded connections. Eighteen of them are facts of that kind — twelve "is a member of this network", six "is in the same place". Move them onto the circles where they belong and the honest size of the relationship graph is five.

Changing that judgement changes nothing in the data. It changes the model, and the same rows are drawn differently. That is what you are doing in the lab.

03Three layers

Renderer, model, data

Everything in this system is one of three things. Keeping them apart is most of understanding it.

LayerWhat it isWhere it lives
Renderer The app itself — one file that draws whatever it is given. It contains the words "circle", "role" and "member" nowhere in its code. index.html, identical byte for byte everywhere
Model What kinds of thing may be recorded, which connections are real relationships and which are attributes, how each is drawn. This is what you design in the lab. schemas/*.json, one per way of reading
Data The actual organisations and connections. Each client's own source — never the lab's

One dataset can have several models. Vale da Lama has three, Barlavento two. Switching between them in the lab is how you argue about the model with the real data in front of you, which is the point.

"Vale da Lama (Holacracy)" is a photograph. "Vale da Lama — LIVE" is a window. They agree today, and nothing tells you when they stop. The names do not warn you, which is a fault of the app rather than of the data.

The lab shows you none of this

There is no line anywhere on screen saying where the thing you are looking at came from. Everything in the table above had to be read out of configuration files. Until that is fixed, this page is the only place it is written down.

05The flow — read this twice

What reaches a client site, and what does not

This is the part that most often gets assumed wrongly, so it is worth stating flatly:

The rule

The app and the models travel from the lab to a client site. The data never does. Every client feeds itself.

The consequence, stated plainly

Editing the Barlavento data inside the lab changes nothing on barlavento.eco. The lab's copy is a sandbox for testing models against something realistic. To change what the community map says, you change the community's source — see section 06.

06Each client's source

How each site feeds itself

Barlavento — the Murmurations directory, plus a holding list

Every morning the site asks a public directory for every organisation tagged barlavento-eco and rebuilds its map from the answer. A member who publishes a profile appears on the map without asking anyone's permission — the directory is polled, not a maintainer.

Organisations that have not published yet are carried in a hand-maintained holding list (curated.json) and marked as recorded about them by somebody else. Every line on the map says which it is. As members publish for themselves, curated rows are replaced and deleted, so that list is a ledger of unfinished business and the map gets more honest as it empties.

Vale da Lama — Notion

Notion holds the circles, roles and people. Every morning a job reads it, rebuilds the map data and commits the result only if something actually changed — so the file's history is the organisation's structural audit trail. To change what the map says, change it in Notion; the map catches up within a day.

CoFundEco — nothing yet

A one-off Kumu export sitting in the lab. There is no CoFundEco site and no refresh. If it needs to become a live map, it needs a source first.

07Doing the work

The four admin jobs

Try a different way of reading the data

Pick a dataset, then switch the model beside it. Nothing is saved anywhere and nothing is published; the map simply redraws. This is the cheapest and most useful thing the lab does, and it is where an argument about the model should happen.

Change what the data is allowed to say

Edit a model file in schemas/. Adding a kind of thing, a kind of connection, or an allowed value is a few lines. Validate then checks the whole file against it and names every rule it breaks — a connection pointing at nothing, a person attached directly to a circle where the model says they must hold a role, a value outside the permitted list.

Send a model to a client site

  1. Change the model in the lab and satisfy yourself with it here.
  2. Copy the changed model file into the client's own repository.
  3. A check compares the copies and complains if they differ.
Step 2 is done by hand

There is no script that promotes a model from the lab to a client. The comparison check notices divergence after it has happened; it does not move anything. Treat "copy it across" as a real task someone must remember, not an automatic consequence of committing.

Stand up a map for a new organisation

  1. Put the organisation's things and connections into two spreadsheet files. Things need an id, a name and a kind; connections need a subject, a kind and an object. Anything else you include is kept.
  2. Write a model declaring the kinds of thing, the kinds of connection, and which may join which. Copy the example and edit it.
  3. Look at the map. Argue. Go back to step 2. This is the actual work, and it is governance work rather than software work.
  4. Write the settings file: title, the single dataset, view mode, and any banner or links.
  5. Later, and optionally, write a loader so the data regenerates from wherever the truth already lives. An organisation whose structure changes twice a year never needs this.
08The client's view

Seeing what end users see

An end-user map is the same app with the admin controls removed and exactly one organisation loaded. It cannot show the other two, because it was never given them.

The obvious way to preview it is misleading

Adding ?mode=view to the lab's address gives you a reader view — of the lab. It carries the lab's title, the lab's missing banner, and a Field Guide button the community site does not have. Worse, the lab opens Barlavento showing 23 lines with Mud Valley Foundation at the centre of everything, while barlavento.eco opens the same data showing 5 lines and no centre, because each lists its two models in a different order.

Today the only faithful preview is opening the real address.

The Vale da Lama site is running an older copy of the app, so its end users are currently offered the dataset switcher, the model switcher and "Re-derive layout" — controls meant only for this room. The simplification was built on 13 September and has not reached that site.

09Traps

Things that have already caught us

  • The forgotten library file. Copying a map into another site means copying five things, and the drawing library is the one everyone forgets. The page then loads looking almost right — title, banner and menus all appear — and the canvas is simply empty. Nothing else produces that particular half-working page.
  • A green check does not mean the website is current. The comparison check reads the repositories, not the published sites. On 1 September the repository was correct, the publish step failed, the check was green, and the site served the old file for hours with nothing announcing it.
  • Turning off the guide link needs the right switch. A setting that looks like it hides the Field Guide button does nothing on its own; only clearing the guide address removes it. That cost an afternoon.
  • An empty answer looks like a real one. A failed download and a file full of nothing are easy to confuse. "Could not look" is not "found nothing".
